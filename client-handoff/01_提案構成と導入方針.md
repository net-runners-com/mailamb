# mailamb: 提案構成と導入方針

## 前提とする環境（お客様事務所）

- 問い合わせ用の**共有メールアカウント 1個**（例: info@〜 / Xserver 等のレンタルサーバ）
- 約5名のスタッフが各PCの Thunderbird からIMAPで同期
- 既存のDraftsフォルダ、Sentフォルダは5名で共有して見える
- Gmail / Workspace は使っていない。アカウント追加発行もしない前提

## 目指す業務の流れ

1. お客様が共有メールアドレスに問い合わせを送る
2. 既存の共有IMAPメールサーバがそのまま受信（原本はInboxに残る）
3. **同じメールが鯖の転送設定でCloudflareにも届く**（Xserverの転送設定を1行追加）
4. Cloudflareの Email Worker が受信した瞬間にAI下書きを生成し、KVに保存
5. いずれかのスタッフが Thunderbird を開いて新着メールを受信
6. **Thunderbird拡張が新着を検知した瞬間、KVから下書きを取り出して共有Draftsに自動保存**
7. 全スタッフのThunderbirdにDrafts下書きがIMAP同期される
8. スタッフが編集して送信（送信は必ず人間）

AIは送信を行いません。送信の判断と操作は、必ずスタッフが行います。
**母艦PCは不要・ポーリング不要・常駐プロセス不要**。既存メール鯖の転送設定とCloudflareだけで完結します。

## 部品ごとの役割

| 部品 | 役割 | 設置場所 |
|---|---|---|
| 既存の共有メールサーバ | 問い合わせ受信（原本保持）、スタッフ側のメール送受信 | **既存のまま（Xserver等）** |
| 鯖側の転送設定 | 届いたメールのコピーをCloudflareへも配送 | **鯖管理画面に1行追加するだけ** |
| CF Email Routing | 転送先として受け取り、Email Worker を起動 | Cloudflare上に新規 |
| `mailamb-email` Worker | メール本文解析、`mailamb` Worker 呼出 | Cloudflare上に新規 |
| `mailamb` Worker | 意図抽出・RAG検索・下書き生成・状態API | Cloudflare上に新規 |
| Workers AI | 意図抽出と返信下書き生成 | Cloudflare |
| Vectorize + D1 + R2 | 社内テンプレ・過去対応の検索 | Cloudflare |
| KV | 下書き本体 / 既読 / 返信中 / 送信済 / IMAP保存claim | Cloudflare |
| Thunderbird拡張 | 新着検知→Drafts自動保存、下書き意図・ヒット表示、既読/返信中/送信済バッジ共有 | 各スタッフPCにインストール |
| Thunderbird 本体 | 最終確認・編集・送信 | 既存のまま |
| 管理画面 (Pages) | ナレッジ追加・編集、問い合わせ活動の閲覧（管理者のみ） | Cloudflare Pages |

## 共有メール運用に合わせた設計のポイント

共有アカウントのIMAPフラグ（既読・送信済）は5名全員で共有されてしまうため、「誰が見た / 誰が返信中 / 誰が送信済」を独立に扱える仕組みが必要です。本構成では Cloudflare 側で管理します。

- **既読管理**: スタッフ別に「このメールを誰が開いたか」を記録。TB拡張のパネルに「👁 既読: tanaka、suzuki」のように表示。
- **返信中（claim）**: スタッフが「下書きで返信」ボタンを押した瞬間に記録。他スタッフのTB拡張に「✏️ 返信中 (XX)」バッジが表示される。
- **送信済（replied）**: 実際に送信した瞬間に記録。他スタッフが同じメールを開くと「✉️ 送信済 (XX)」が緑バッジで表示され、二重返信を防ぐ確認ダイアログが出る。
- **IMAP APPENDの重複防止**: 5台のTBが同時に新着検知しても、Cloudflare側で原子的に「保存者」をロック（`imap-saved`）するため、Draftsに同じ下書きが複数作られない。
- **既読フラグを立てない**: 拡張側の処理は TB の内部APIを使うため、IMAPの `\Seen` フラグには影響しない。

## 本番の遅延イメージ

| タイミング | 処理 |
|---|---|
| 0秒 | お客様がメール送信 |
| 2〜10秒 | Xserver受信、CF Email Routingへ転送、Email Worker 起動 |
| 10〜25秒 | Workers AI で意図抽出・RAG検索・下書き生成、KVに保存 |
| （この時点でAI下書きは準備完了。TBが起動していれば即Draftsへ） |
| ある時刻T | いずれかのスタッフがTBを開いて新着受信 |
| T + 1秒 | TB拡張が新着検知、KVから下書き取り出し、Draftsに自動保存 |
| T + 数秒 | 他スタッフのTBにIMAP同期で下書きが見える |

スタッフが対応開始した瞬間に下書きが既に用意されている状態になります。深夜や休日に届いた問い合わせも、翌朝TBを開けば即座に下書きが Drafts に並びます。

## この方針を選ぶ理由

既存の共有IMAP運用を変えずに済むため、現在のお客様の業務フローへの影響が最小です。MX、SPF、DKIM、DNS設定は一切変更しません。鯖側に転送設定を1行追加するだけで、Cloudflare がリアルタイムでメールを受け取れます。母艦PCの常駐や朝のバッチ処理は不要です。

もし Cloudflare 側が落ちても、通常のメール送受信は既存鯖で引き続き動作します。下書きが出なくなるだけで、業務は従来通りに手動返信できます。

## まだ確定していないこと

この資料は、コンサルから示された提案構成を基にしています。現在の環境で実際に使えるかは、次を確認してから決めます。

1. 既存共有メールサーバ（例: Xserver）の **転送設定の可否**（info@〜 に届いたコピーを外部ドメインへ配送できるか、SPF等への影響）
2. 転送先ドメイン（Cloudflare Email Routing 用）の DNS 設定場所
3. 共有Draftsを複数PCが同時に編集した時の挙動（楽観ロック無し、後保存勝ち）
4. **二重返信防止**を運用（担当宣言）か技術（Cloudflare側の送信済み共有）どちらで担保するか
5. 過去対応や社内資料を、どこまでCloudflare上の検索用データとして使ってよいか
6. 顧客情報の匿名化・マスキングの範囲
7. Cloudflare アカウントを 当社が運用する形か、お客様専用に発行するか
8. 各スタッフPCへのThunderbird拡張配布（未署名拡張の導入方針）
9. お客様へのプライバシー表記更新の要否
10. 全員がTBを長期間開かない期間が発生する業務形態か（Yes の場合は補完として常駐処理を追加検討）

この確認をせず、本番メールの流れを変更することはありません。
